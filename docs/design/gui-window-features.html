wowdps-gui — the window frontend

What the windowed GUI does today, a visual language borrowed from Archon's class-accented layouts, the features worth building, and a callout tour of the proposed screens. Overlay-only surfaces are out of scope.

1. What the window does today

The window (wowdps-gui, no --overlay) is a pure rendering client over ClientState. Everything it shows arrives as a daemon snapshot for one declared cursor.

The gap, stated plainly

The daemon already answers far more than the window asks. On the wire, never rendered by the GUI:

  • The whole history store — GetHistory, GetFight, PinFight, ImportLog, Regrade, HistoryChanged (v20+). Only wowdps-mcp and wowdps-history use them.
  • Multi-death recaps — Breakdown::deaths[] and death_index (v28). The window can only ever show one death window.
  • Stacking debuffs — stacking, stacks, stack_base (v27, R21). Zero references in crates/gui.
  • Mitigation arrives as a full record and renders as one line of text.
  • Effective DPS, support, uptime, shields (R18–R20) — answered for stored fights, visible only through MCP.

Visually the window is honest but plain: flat panels, one accent, sizes chosen per call site, and a 90-character hint string as the only affordance. Everything below fixes both halves at once.

2. Visual language

Four things make Archon's pages read well, and all four are portable to iced.

2a. The spec color is the theme

Archon derives every accent — headings, links, the active tab's gradient, the bar fills — from the class being viewed, so a Havoc page is unmistakably purple and a Frost DK page unmistakably red. We already know the owner's class and spec (COMBATANT_INFO, or R8 inference), and we already ship the class crest and spec icon. So: one --spec accent, resolved from the pinned player's spec, drives the chrome. Row bars keep each player's own class color — that is data — but tabs, selection, focus rings, links and headings all take the accent.

--spec --spec-2 (lift) amount bar pet / secondary rate column headline number % badge

The derivation is mechanical, so it needs no per-class hand-tuning: --spec is the class color the model already returns from Class::rgb; --spec-2 is that color lifted 35% toward white, or darkened 45% when the class color is already light (relative luminance over 0.6 — Rogue, Priest, Monk, and Warrior at the boundary); the gradient always runs --spec-2 → --spec; and text drawn on the accent flips to near-black for those light classes — the same rule view.rs’s inverted_metrics already applies to bar labels. Headings take whichever end of the pair is brighter, so a Priest reads white-on-dark and a Death Knight reads lifted-red.

Every class, same chrome: two-tone title, active tab, headline card, two bars.

Three of these are where a naive “just use the class color” breaks. Priest is pure white, so the accent can differ from ordinary text only by weight and by the gradient’s dark end. Rogue and Monk are bright enough that white text on the accent is unreadable, which is what the ink flip is for. Warrior sits right on the luminance boundary, so it is the case to check first when tuning the threshold. Everything else follows the rule without argument.

Spec, not just class, is available (Spec::from_id via COMBATANT_INFO, else R8 inference), so a later refinement can tint within the class — Fire vs Frost Mage — without changing anything structural. Class alone is the honest default, because R8 can identify a class from a shared cast when it cannot pin the spec.

The two-tone heading — Havoc Demon Hunter Raid Enchants — is the cheapest borrowable trick on the whole site: the colored half names who, the white half names what. Our header becomes Tranqster · damage taken.

2b. Bars belong inside the table, not instead of it

Archon's throughput tables put a gradient bar in an Amount column beside real columns — casts, CPM, avg cast, hits, avg hit, crit, uptime, DPS — with the rate column in green and the total pinned in a footer row. That is strictly more information per pixel than our current "bar with three numbers painted on it", and it makes the columns sortable in an obvious way. Our by-spell drill has every one of those numbers already (Row carries count, crits, per_sec, pct, extra).

2c. Mirrored two-column item layout

The gear page pairs slots left/right around a centre gutter, icon on the outside, name and sockets inside, popularity in the middle. It reads as a paper doll without being one, and it survives narrow widths by collapsing to one column. Our talent viewer's inventory tab currently renders item {id} rows in slot order; this is the layout it wants.

2d. Time is a lane, and lanes have category toggles

The Rotation page's opener/cooldown views are lane charts: a left column carrying each parse's DPS, a shared ruler, and icon ticks on the track — with checkbox groups (offensive / defensive / utility / externals) filtering which lanes show. That is exactly the shape our R18 uptime data wants, and the same widget serves three of our screens: uptime lanes, per-pull comparison, and cooldown usage.

Feasibility, since this is iced and not CSS: gradients are a canvas fill or a stacked container; the lane chart is one canvas with hit-testing we already do for compare graphs; the mirrored grid is two columns of row!. The one genuinely new primitive is a sortable table header, and the caption line is already laid out over its columns.

3. Proposed features

3a. Usability

P0Icon tab bar + jump chips Archon's two-row nav: a tab strip of the seven views (each with its spec/school icon, the active one on a spec gradient) and a "jump to" chip row for sections within the current screen. Replaces "read the footer string and hope"; the key hints ride on the tabs so the keymap still teaches itself.
P0Filter box One field filtering rows by player or spell name, client-side over the snapshot — no round trip, survives the 10 Hz refresh.
P0"Me" pinning + spec accent Pin one player as the owner; their row is outlined and kept in view, and their spec becomes the window's accent color. One setting, two payoffs.
P1Sortable columns Click a header to sort by amount / rate / % / crit / count, click again to reverse, with the sorted header marked. Turns one chart into six questions.
P1Column chooser Archon's "Show All Columns" checkbox: a compact default set, and an opt-in wide set (avg hit, uptime, miss%, overkill).
P1Shortcut sheet (?) A modal card of every binding, grouped — which lets the footer shrink to two contextual hints.
P1Grown options panel Density, number format, colorblind-safe bars, default view, accent source (spec vs fixed), effective-vs-raw default. Today: one checkbox.

3b. Information

P0Throughput table The by-spell drill becomes Archon's damage-breakdown table: gradient amount bar in-column, plus casts, CPM, avg hit, crit%, uptime, rate — expandable rows for pets and sub-spells, a pinned total row. All from fields Row already carries.
P0Home dashboard A statistical front door over the history store: season top-line, Mythic+ by key, raid progression, the owner's own trend, the characters you play, and the last day of fights — every panel a jump point into the screen that owns it. Also the fix for "the app opens on a blank meter when nothing is happening".
P0A stated view map Eleven surfaces need a navigation contract: ~ to Home from any depth, Esc always one level up, every stats surface opening pulls into the ordinary meter. Written down once, honoured by every screen.
P0History screen Encounter × difficulty progression, per-pull grade and rank, trend sparkline, pin/unpin, "open this stored fight" into the normal meter. GetHistory/GetFight/PinFight already exist daemon-side.
P0Summary band Archon's stat cards, ours: duration, raid rate, your effective DPS, your rank in role, delta vs your best pull, deaths, key timer. The headline number in orange, the top card on the spec gradient.
P0Death recap navigator deaths[] as a chip strip (one ⚰ per death with its clock time); clicking re-requests that death_index. Today the window shows one of three with no hint the others exist.
P1Cast timeline Warcraft Logs' per-ability cast chart: legend chips as series toggles, a cast-time histogram over the lanes, cast bars with icons, a by-source mode putting the boss on the same ruler, and a filter-expression field. The one proposal needing engine work — SPELL_CAST_START is not parsed today.
P1Uptime lanes with category filters The cooldown-timeline widget over the taken series: lanes for defensives, offensives, externals and trinkets, each group checkbox-toggled, all sharing the fight ruler.
P1Mitigation cards + miss chips Absorbed (partial/full), blocked, staggered vs stagger-ticked, dodge/parry/miss/immune counts, DTPS — cards and chips instead of one sentence.
P1Stack matrix Rows = damage ability, columns = debuff stack level, cells = average hit, heat-shaded. The question R21 exists to answer, rendered nowhere today.
P1Loadout page, Archon-style The talent viewer's inventory tab as the mirrored gear grid: icon, name in spec color, enchant/gem chiplets, secondary-stat pair, item level in the gutter — for the logged COMBATANT_INFO gear and for a SimC paste alike.
P2Absorb ledger Healer tab: per shield spell, applied / consumed / wasted / efficiency, unknown left honestly blank (R20's None, never a silent 0).
P2Effective vs raw toggle R19 in one control, with the supporter's given/received on their row. An Augmentation Evoker makes the raw chart lie.

4. Layout tour

Layout A — Home: the statistical front door

Today the window opens on whatever the daemon is watching: a live meter, or a segment list. That is the right answer during a pull and the wrong one every other time — it answers "what is happening" when the question is usually "how am I doing, and where do I go to find out". So the app gets a Home surface: a read-only dashboard over the history store, every panel of which is a jump point into the screen that owns that data.

Layout A — Home, the first surface. Read-only; nothing here needs a live daemon.

  • 1Character and season selectors (top). A card stores its owner guid and every player's guid, name, class and spec, so "which of my characters" is a filter, not a new concept. Season is the one genuinely new idea: cards carry build and a UTC timestamp, so a season is a named date range in config (start date + label), and everything on this screen is scoped by it.
  • 2Top-line cards. Season score, keys timed, raid bosses down, fights stored, best week. Each is a count or a max over the card index the daemon already keeps in memory — no log parsing, no DuckDB.
  • 3Mythic+ by key. One row per dungeon at its best level, with runs and the timed/over split. FightKind::Key cards carry KeyInfo (map, level, completed) and pars_ms, so "timed" is the comparison R10 already defines rather than a guess. Clicking a row opens the key table filtered to that dungeon.
  • 4Raid progression. Bosses in encounter order with the best result per difficulty and this week's pull count — the Progression query, one row per boss instead of one screen per boss.
  • 5Me. The owner's own numbers for the selected character: median and best effective DPS, rank within role, deaths per pull, and a twelve-point sparkline. All of it is Trend with the role's default measure — a healer sees HPS, a tank sees DTPS and AM uptime, because the grader is already role-relative.
  • 6Characters. Every character the store has seen you play, with its class color and score; picking one re-scopes the whole screen. This is the "teams/characters I play" jump point, derived from card owners rather than any new bookkeeping.
  • 7Season progress by role. One bar per role you actually play, with the trailing weekly curve underneath. Percentile is against your own history, stated as such — we have no ladder, and claiming otherwise would be the one dishonest number on the page.
  • 8Recent. The last day of fights, keys and raid alike, pins marked. It is the fastest path back to "the thing I just did", which is what people actually open a meter for after a run.
What Home costs. Every panel is an aggregate over the daemon's existing card index, so the honest options are: compute it client-side from a wide Fights answer (works today, no wire change, a few hundred cards to page through), or add one HistoryQuery::Summary that answers the whole screen in a single reply (cheaper on the socket, one PROTO_VERSION bump). Start client-side, since the shape of the dashboard will move around before it settles; promote to a query once it stops changing. The season range and the character list belong in config.toml either way.

Layout B — Screen::Meter, ~900×620.

  • 1Selector bar (top). Archon's Class/Spec/Content/Difficulty row, ours as fight / pull / scope / basis / you. Each is a small labelled dropdown, so the four questions that change what the numbers mean live in one place instead of being scattered across keys, the segment list and the options panel.
  • 2Icon tab bar. The seven views plus History, each with its icon; the active tab wears the spec gradient. Key hints stay beside the labels. This is the fix for "there is no on-screen view control at all".
  • 3Jump chips. Sections of the current screen — chart, timeline, deaths, loadout. On a tall window they scroll to the section; on a short one they switch it. Cheap, and it makes the meter feel like a page rather than a panel.
  • 4Two-tone title. Encounter name in the accent, everything else white/dim, outcome tag colored. Section 2a.
  • 5Stat cards, headline on the gradient. Your effective DPS gets the spec-gradient card; rank, delta vs your best, raid rate and deaths follow in plain cards with colored numbers. The answer to "how did that go" before any drilling.
  • 6Filter strip. Row filter, the effective/raw basis pills (R19), the Σ-visit fold, and the show-all-columns checkbox on the right — Archon's own control, in Archon's own position.
  • 7The chart as a table. Rank, class-icon + name in the accent, the gradient amount bar in its own sortable column, then dps / share / crit / deaths. The selected row is tinted rather than outlined, and a pinned total row closes the table. Sorting by crit or deaths asks a different question of the same pull without leaving the screen.

Layout C — the drilldown, restyled as Archon's Damage Breakdown.

  • 1Icon tiles with badges (above the table). Four derived headline facts — a cooldown's uptime, casts of a spell that should never sit on cooldown, trinket uses, biggest hit — each an actual spell icon from spell-icons.bin with a ring in the accent and its number on a pill. Archon uses this shape for popularity; ours carries per-pull facts, and it gives the top of the drill a face instead of a wall of digits.
  • 2Sortable column set. Amount (bar), share, casts, CPM, avg cast, hits, avg hit, crit, uptime, DPS. Every one of these is already in Row or derivable from it; today the drill shows three of them. The default view hides the last four behind show all columns.
  • 3Gradient bars inside the Amount column. Periwinkle→magenta for the player's own abilities, periwinkle→red for pet and guardian rows, so R4's ownership fold is visible at a glance rather than an asterisk in a footnote.
  • 4Rollups that expand (▾). A parent row is a rollup — a pet with its own spellbook, a summon, an aura with its ticks, a spell with ranks — and the disclosure indents its children into the same columns, on the same amount axis, each with its own share of the fight total (so children sum to the parent, and the bar lengths stay comparable across the whole table). This is how Archon renders Dominion of Argus over Mind Sear / Shadow Nova / Blaze, and it is the right answer to a question our meter currently ducks: R4 folds a pet onto its owner, and today that fold is invisible. Rollup children come free — Segment keys by raw guid before folding, so the split already exists in the engine.
  • 5Pinned total row. The fight's totals in the same columns, so a per-ability number always has its denominator on screen.
  • 6"During cooldowns" jump chip. Archon's Damage Done during Summon Demonic Tyrant table, ours as: the same breakdown restricted to the window where a chosen cooldown was up (we have the R18 spans and the 1 s timeline to slice by). This is the single most actionable table on their site, and we can build it from data we already store.

Layout D — the drilldown on View::Taken.

  • 1Mitigation cards + miss chips. The single drill_mitigation_line becomes five cards and a chip row. Cards compare across pulls; a sentence does not.
  • 2Stack matrix (R21). Rows are the abilities that hit you, columns the open debuff's stack level, cells the average hit, heat-shaded green→amber→red. Reading across a row is the whole ruling: how much worse does this get per stack. Column 0 is the reader's derived baseline, so the "unstacked" number is always honest.
  • 3Category filter groups. Archon's checkbox groups over the cooldown timeline — defensive / externals / offensive / trinkets — deciding which lanes render. A tank looking for a missed Shield Block does not want six offensive lanes in the way.
  • 4Lane chart with a left value column. Same widget as Archon's rotation view: the shared ruler up top, each lane's headline number on the left (DTPS for the damage series, uptime % for a span lane), spans on the track. Externals get their own color and name their caster.
  • 5Alignment is the analysis. A red spike over empty lanes is a missed cooldown; the same spike under a green span is just a big hit. The footer states the worst instance in one sentence, derived from what is already drawn.

Layout E — a per-ability cast timeline, new.

  • 1Legend chips as series toggles. Every ability the subject cast, each a chip that lights its lane. This is the same control as the cooldown-timeline's category groups, one level finer — and it doubles as the legend, so no separate key is needed.
  • 2Filter expression field. A one-line query over the events feeding the chart (type=cast and target=boss). Start with three or four keys — type, ability, target, source — parsed by a small stdlib matcher; unknown keys highlight rather than error.
  • 3The "time spent casting" histogram. One bar per cast, height = cast time, above the lanes and on the same x-axis. A gap in that strip is dead GCD time, which is the single most useful thing a rotation chart shows and takes almost no space.
  • 4Cast bars, not just ticks. Each cast is an icon at its start plus a bar as long as the cast took; instants are the icon alone, channels get the full bar. Empty lanes stay visible (dimmed) — "Blazing Barrier: never cast" is itself a finding.
  • 5Enemy lanes on the same ruler. Switch lanes from by ability to by source and the chart becomes the second reference shot: the boss and each add on its own row, so a player's casts and the boss's mechanic line up on one axis. Everything the meter already knows about enemy casts appears here for free.
  • 6Hover reads the log back. Two lines, exactly as the log recorded them: begins casting at t, casts on target at t. It makes the chart auditable against the file, which fits a tool whose fixtures are hand-verified.
What this one costs. Unlike every other layout here, the cast timeline needs engine work: the parser turns SPELL_CAST_SUCCESS into Event::Cast but SPELL_CAST_START currently falls through to Event::Other, so cast durations are not recorded anywhere. The change is a new event, a per-segment cast list (start, success/failure, spell, target, source), a snapshot field, and therefore a PROTO_VERSION bump — plus a fixture with a started-but-interrupted cast, because the pairing rule (start with no success = cancelled) is exactly the kind of thing CONTRACT.md exists to fix in writing.

5. Suggested order

  1. The visual language itself. Spec accent, gradient bars, two-tone titles, one type scale, stat cards. It touches view.rs broadly but changes no data flow, and every later screen inherits it.
  2. Home and the view map. The dashboard reads the history store client-side through the existing Fights query, and the map settles ~ / Esc before more screens exist to get lost in. Doing this second means every screen after it has a place to be reached from.
  3. Tab bar, filter, ? sheet, me-pinning. Pure client work over data already on screen; makes everything after it discoverable.
  4. Throughput table with rollups + death navigator + mitigation cards + stack matrix. Renders wire fields the daemon already sends and the GUI drops on the floor — the highest information gain per line of code in the whole list.
  5. History screen and the lane chart. New client state against existing v20 messages; the lane widget is then reused by the uptime lanes.
  6. Uptime lanes, absorb ledger, "during cooldowns" table. These need R18/R20 data on the live snapshot path, so they carry a PROTO_VERSION bump.
  7. The cast timeline. Last, because it is the only item that starts in the parser: SPELL_CAST_START, a cast list on the segment, a fixture for the cancelled-cast rule, then the wire and the chart. It reuses the lane widget built in step 4, so by then it is mostly engine work.
Anything in step 5 changes the wire shape, which per CONTRACT.md means the contract, the golden bytes in crates/proto/tests/codec.rs and the code move together — and PROTO_VERSION bumps once for the batch, not once per feature.
