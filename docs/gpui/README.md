# GPUI reference for `crates/gui-new`

`crates/gui-new` will re-implement the window and the overlay (today
`crates/gui`, on iced + iced_layershell) on Zed's **GPUI**, with **GPUI Kit**
(longbridge, formerly gpui-component) for its components. This directory is
the offline reference for that work. Only this README and `.gitignore` are
committed; the mirror beside it is regenerated by

```sh
tools/fetch-gpui-docs.sh            # newest gpui-kit, ~10 s, ~26 MB
tools/fetch-gpui-docs.sh 0.7.0      # or pin a Kit version
```

`VERSIONS` records what was fetched and when. The mirror is gitignored, and
ripgrep honours that, so the Grep tool skips it unless you point it at the
directory. Use `grep -rn … docs/gpui/` or pass the path explicitly.

## Which GPUI: `gpui-pre`, not `gpui`

crates.io's `gpui` (what <https://docs.rs/gpui/latest/gpui/> shows) is
**0.2.2, last published 2025-10**. GPUI Kit does not use it. Kit pins
`gpui-pre`, a crates.io publication of a recorded Zed commit whose library
name is still `gpui`, *exactly* (`=0.3.7` for Kit 0.7.0, a new snapshot about
weekly). Every API link in Kit's own pages points at
`docs.rs/gpui-pre/<pin>`. The two diverge in ways that matter here; the first
item under *Findings* (layer-shell windows) does not exist in 0.2.2 at all.
So:

- **target `gpui-pre` (through `gpui-kit`)**: `api/gpui-pre-*/`, `src/gpui-pre-*/`
- `api/gpui-0.2.2/` is the docs.rs page the work started from, kept for
  comparison only

Kit's crates move in lockstep: `gpui-kit` (a facade: `use gpui_kit::*;` is
GPUI; `gpui_kit::{base, component, assets, platform}` are the layers),
`gpui-base` (unstyled behaviour: primitives, Plot, VirtualList, Motion,
text selection), `gpui-component` (the styled library: Root, Theme, DataTable,
Tabs, Command, Chart …), `gpui-kit-assets` (icons). The gpui snapshot is a
family too: `gpui-pre` (the framework), `gpui-pre-platform`
(`application()` / `headless()` / `current_headless_renderer()`),
`gpui-pre-linux` (Wayland + X11 backends), `gpui-pre-wgpu` (the renderer and
text system on Linux) and `gpui-pre-macros`. Never override one of them to a
different version; Kit's install page says so too.

## Reading order

For someone coming from iced, in this order:

1. `kit/docs/getting-started.md`, `render.md`, `entity.md`, `context.md`.
   The model is entities (state owned by the `App`) plus `Render` views, not
   iced's `update`/`view` over one message enum. Then
   `src/gpui-pre-0.3.7/src/_ownership_and_data_flow.rs` (a docs-only module,
   also in its digest) and `src/gpui-pre-0.3.7/docs/{contexts,key_dispatch}.md`.
2. `element.md`, `element_id.md`, `render-once.md`, `view-cache.md`: element
   identity and the state that survives frames.
3. `window.md`, `multi-window.md`, `event.md`, `action.md`, `keybinding.md`,
   `focus.md`: input, plus `actions!` / key contexts, which take the place
   of `keys::action_for`.
4. `style.md` (Tailwind-shaped `Styled` methods), `geometry.md`, `fonts.md`,
   `text-system.md`, `paint.md` (the `canvas()` element + `PathBuilder`, which
   is how the graphs get drawn).
5. `task.md` (foreground/background executors; dropping a `Task` cancels
   it), `test.md`.
6. Components the window needs: `component/root.md` (every window's root,
   for dialogs and notifications), `theme.md`, `table.md` / `data-table.md`,
   `virtual-list.md`, `tabs.md`, `tooltip.md`, `command.md` (the palette),
   `popover.md` / `menu.md`, `scrollable.md`, `notification.md` (toasts),
   `kbd.md`; `base/plot.md` + `component/plot.md` / `chart.md` for the
   ribbon and inspector graphs.
7. Examples worth reading whole, in `src/gpui-pre-0.3.7/examples/`:
   `layer_shell.rs`, `testing.rs`, `painting.rs`, `uniform_list.rs`,
   `data_table.rs`, `text.rs`, `window_positioning.rs`, `tab_stop.rs`.

## Findings that shape gui-new

Checked against the 0.3.7 sources on 2026-09-30; file:line pointers are
into `src/`.

**The overlay is possible on stock gpui-pre.** `WindowKind::LayerShell(
LayerShellOptions { namespace, layer, anchor, exclusive_zone, exclusive_edge,
margin, keyboard_interactivity })`
(`gpui-pre-0.3.7/src/platform/layer_shell.rs`, the full example is
`examples/layer_shell.rs`). The Wayland backend builds a
`zwlr_layer_surface_v1` from it (`gpui-pre-linux-0.3.7/src/linux/wayland/window.rs:156`).
A compositor without wlr-layer-shell gets `LayerShellNotSupportedError`.
Wayland only (feature `wayland`, on by default); X11 has no equivalent.
Around it:

- **Click-through:** `Window::set_input_region(Option<&[Bounds<Pixels>]>)`.
  `Some(&[])` takes no pointer input at all; `None` restores the whole
  surface (`gpui-pre-0.3.7/src/window.rs:2414`). The iced overlay's "hidden
  = a 1×1 click-through surface" can become an empty input region over a
  transparent frame, or a closed and reopened window. That is a design
  choice, not yet made.
- **Which monitor:** `WindowOptions::display_id` becomes the layer
  surface's `wl_output` (`gpui-pre-linux-0.3.7/src/linux/wayland/client.rs:1162`).
  `PlatformDisplay` exposes `id()`, `uuid()` and `bounds()` but no output
  name, so turning Hyprland's monitor name into a `DisplayId` probably means
  matching bounds against `hyprctl monitors`. Verify this before relying on
  it.
- **Resize:** `Window::resize` becomes `layer_surface.set_size`
  (`wayland/window.rs:423`); the surface can grow for a comparison as it does
  now. `Window::set_exclusive_zone` / `set_exclusive_edge` exist too.
- **Transparency:** `WindowOptions::window_background =
  WindowBackgroundAppearance::Transparent`, as the example does.
- **Not through Kit's Root** (found in step 1.1). `gpui_kit::open_window`
  wraps the view in Root, and Kit's component layer then paints the
  theme's ground under it and, on a client-decorated surface, a 20 px
  shadow border (`window_border`) that it also sets as the client inset.
  A layer surface never leaves client decorations
  (`gpui-pre-linux-0.3.7/src/linux/wayland/window.rs:616`), so a 28 × 96
  tab mapped as 68 × 136. Open the overlay's view with `cx.open_window`.
- **Keyboard:** `KeyboardInteractivity::{None, Exclusive, OnDemand}`
  (`layer_shell.rs`). `None` matches today's keyboardless overlay.
- The two iced_layershell 0.19 bugs `overlay.rs` works around (a bare
  `SizeChange` dropped; a custom `scale_factor` breaking hit-testing, see
  `docs/tracing.md`) belong to that crate and do not carry over. Re-check
  fractional scaling on the real monitor anyway.

**Headless review still works, through wgpu instead of tiny-skia.** Under
the `test-support` feature: `TestAppContext` / `VisualTestContext`
(deterministic `TestPlatform`), `HeadlessAppContext::with_platform(text_system,
assets, || gpui_platform::current_headless_renderer())`, `Window::render_to_image`
and `capture_screenshot`, plus `Window::painted_quads()` to assert on the
scene without rasterizing (`gpui-pre-0.3.7/src/window.rs:2705`,
`app/headless_app_context.rs`). On Linux, `current_headless_renderer()` is
`gpui_wgpu::WgpuHeadlessRenderer` (`gpui-pre-platform-0.3.7/src/gpui_platform.rs:85`),
so it needs a wgpu adapter: a real GPU, or Mesa's lavapipe software Vulkan
in CI. **Kit's `kit/docs/test.md` still says headless rendering is macOS-only;
that page predates this pin.** The design-shot / overlay-guard loop in
`crates/gui/SHOTS.md` can be rebuilt on this. Hashes will differ from iced's
anyway, so gui-new blesses its own.

**Click-through tests need no screenshots: use Kit's own harness.**
`gpui_kit::test::TestWindowExt` (feature `test-support`, dev-dependency only)
drives the real view in a headless `TestAppContext` window: `find(id)` /
`try_find`, `within(scope)`, `click` / `click_at` / `right_click` /
`double_click` / `hover` / `scroll` / `drag_to`, `press("j")`, `input(text)`.
These go through GPUI's native hit testing and key dispatch. An
`ElementSnapshot` reads back `role`, `label`, `value`, `checked`, `selected`,
`expanded`, `bounds`, `visible` and `focused` from the native accessibility
properties (`src/gpui-kit-0.7.0/src/test.rs`,
`src/gpui-base-0.7.0/src/test_support.rs`; the guide is
`kit/docs/test.md` from "Choose stable test targets" on). Kit controls
register themselves; our own divs opt in with `.id("…").test_support()`.
Two limits shape gui-new:

- **No visible-text getter.** Assert through an `aria_label` that already
  means something, or by reading the view entity.
- **A canvas is one opaque target.** For the graphs, ribbon and lanes, wrap
  the canvas in an id'd `.test_support()` div, `click_at` an offset, and
  assert the app state.

The harness drives the view in a test window, so layer-shell behaviour
(input region, output choice) still needs the live compositor. It is young
(first commit 2026-09-08, in Kit since 0.6.6, public API unchanged into
0.7.0), but it is the vendor's own and Kit tests itself with it (278 test
functions in `src/gpui-kit-0.7.0/tests/`). Underneath it is gpui-pre's
`VisualTestContext` (`simulate_click`, `simulate_keystrokes`,
`dispatch_action`, `debug_selector` + `debug_bounds`), usable directly where
Kit's layer is not.

Third-party GPUI automation, surveyed on GitHub 2026-09-30, is all a few
weeks or months old, from one or two authors, and none fits without a cost:

| Repo | Verdict |
| --- | --- |
| themixednuts/gpui-mcp | Most capable live driver: an automatic AccessKit tree and per-frame cost reports, supports Kit 0.7.0, CI green. But it needs a 1,514-line patch over gpui-pre, re-vendored for each weekly snapshot, and Linux window capture is X11-only. |
| stefan-siebert/gpui-mcp | Record/replay and goldens, but needs a Zed fork plus a gpui-component fork, not Kit. |
| maui1911/gpui-driver | No fork on Linux (public `Window::dispatch_event`), but built against Zed git gpui, Linux untested, idle since 2026-06. |
| hexuria/gpui-agent | Kit 0.6, no fork, 314 tests, CI. But the app hand-writes its whole semantic tree and dispatch. |
| jakejarrett/gpui-mcp, emakarov/gpui-agentic-http | 1 and 10 commits; protocol shells with no GPUI integration. |
| stolinski/gpui-agent | 1 commit, macOS-first, needs a paid model API and a gpui-pre 0.3.5 patch. |

The `gpui-ce` fork (community edition, `a11y_tree()` for tests) is ruled out
as a base: no forked GPUI.

**Fonts are bundled the same way.**
`cx.text_system().add_fonts(vec![Cow::Borrowed(include_bytes!(…))])` before
opening a window (`kit/docs/fonts.md`). The Barlow Semi Condensed Tabular and
Marcellus files under `crates/gui-logic/fonts/` serve both GUIs as assets. On Linux the
text system is cosmic-text + swash inside `gpui-pre-wgpu`.

**What maps onto what** (a first reading; each needs proving in code):

| iced today (`crates/gui`) | GPUI / Kit |
| --- | --- |
| `Gui` + `Message` + `update`/`view` | entities + `Render` views; `cx.notify()`; events via `EventEmitter` / `cx.subscribe` |
| `keys::action_for`, window-local keys | `actions!` + `KeyBinding::new("j", Down, Some("Meter"))` + `.key_context(…)` / `.on_action(…)` |
| canvas graphs, ribbon, lanes, `line_icons.rs` | `canvas()` + `PathBuilder` (`kit/docs/paint.md`); gpui-base `Plot` for scales/axes/hover |
| `table.rs` list primitive | `uniform_list` / `list` (virtualized, in gpui) or Kit `Table` / `DataTable` / `VirtualList` |
| `ellipsis.rs` custom widget | text truncation in `Styled` (`text_ellipsis`, `truncate`; check `style.md`) |
| palette, `?` sheet, menus, toasts | Kit `Command`, `Dialog` / `Sheet`, `Popover` / `Menu`, `Notification` (all need Kit's `Root`) |
| the daemon client's threads + `drain_client` tick | `cx.spawn` / `background_spawn` + a timer or an async channel; GPUI brings its own executors, no tokio |
| `theme.rs` tokens, `Look` | Kit `Theme` (colours, radii, fonts) or plain constants; `Look::OVERLAY` pixels are iced's and will not carry over byte for byte |

**Policy and build cost, to settle before the crate's first commit.**
CONTRACT.md approves iced + iced_layershell + serde/toml for the GUI and bans
any iced feature that pulls a crate. GPUI is a much larger tree: gpui-pre's
own lockfile has 532 packages, it is edition 2024, Kit asks for Rust ≥ 1.92,
and it pulls wgpu, cosmic-text, taffy, image, resvg, serde/serde_json and
chrono transitively. gui-new needs its own line in the dependency policy.
The Linux build wants fontconfig, wayland, libxkbcommon(-x11), x11-xcb,
openssl, zstd and a Vulkan loader + driver (`kit/docs/installation.md`), so
the flake/devenv shell (`nix/dev/env.nix`) and probably a `build.rs`
RUNPATH bake like `crates/gui/build.rs`'s will need extending. Kit also
suggests `[profile.dev.package]` opt-level 3 for the gpui-pre / Kit crates
(plus taffy, rustybuzz, ttf-parser) so debug builds render at a usable speed.

**Kit's styled `Input` decides its own colours and size.** It rewrites
the state's `InputEditorStyle` from the global theme on every render
(`gpui-component-0.7.0/src/input/input.rs`, around line 544), so a
placeholder is always the theme's one `muted_foreground` — shared with
Kit's tooltips, tabs and keycaps — and its frame sets the text size
through `input_text_size` (`text_sm` at `Medium`; `Size::Size(n)` gives
`n × 0.875`), which only `.text_size()` on the `Input` itself overrides. A
field that must look like the app's own composes gpui-base's unstyled
`gpui_kit::base::input::Input` on the same `InputState` and calls
`set_editor_style` itself each render (Kit's own docs describe this:
`kit/base/primitives/input.md`). Caret, IME, selection, scrolling and
clipping stay the engine's. gui-new's `window/field.rs` is that field.
Drawing a placeholder over an empty field instead goes wrong under IME
composition (the text changes without a `Change` event), at a zoom (Kit's
caret follows its `Rems(1.25)` line, not ours) and with long words.

**An animation frame redraws the whole view.** GPUI's animation frame
notifies the view that asked for it, and a window built as one root view
rebuilds its whole tree each frame. gui-new's window idled at 5.7 % of a
core (iced: 2.0 %) while an endless pulse ran on its live dot, about 28
renders a second; three pulses per live pull brought it to 0.4 %. Keep
every animation finite and keyed to what triggered it, settle to the
static pixels, and give anything that must keep moving (the overlay's
staleness radar) a timer at the slowest rate that still reads as motion.
