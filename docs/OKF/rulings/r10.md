**The call:** Difficulty ≠ 0 zoning opens a visit (suspend/resume on zoning; keyed visits resume on map alone), and so does a pull behind a door logged at 0 — an ENCOUNTER_START while zoned out zones in, and is a seed line ([the decision](../decisions/a-pull-zones-in.md)); CHALLENGE_MODE_START resets the visit and CHALLENGE_MODE_END closes it (and keys a run joined mid-way, on the span the log saw); Σ = members merged, duration = Σ of member durations — except a keyed Σ runs on the KEY clock and reports the TIMED verdict vs par. Every Σ's RATES run on Σ of its members' combat clocks ([R7](r7.md) amendment, 2026-10-02) — a key's included; its RUN rate (amount ÷ key clock) is a reader's sum (v40, [the decision](../decisions/match-the-game-meter.md)).

**A conflicting change would:** Split or merge runs wrongly, mis-time keys, or break index/lazy/replay agreement on ordinals.

## Detail

A ZONE_CHANGE with difficulty ≠ 0 opens a *visit* (map_id + difficulty + zone name); ordinals index the file's visit table in order. Zoning out (difficulty 0) SUSPENDS it — segments recorded outside carry no visit — re-entering the same (map_id, difficulty) resumes it; a different instance closes it. A KEYED visit resumes on map_id alone: mid-run re-fires (reloads, reconnects) carry the keystone difficulty instead of the one stamped at the door, and a split would orphan the END onto an unkeyed visit. • Every CHALLENGE_MODE_START on the current visit's map is a visit boundary — the dungeon resets and the key's clock starts with the countdown, not at the door: the visit (and any open trash) closes and a fresh KEYED visit opens, so pre-key activity never joins the run's Overall. The START is AUTHORITATIVE (amendment, 2026-09-12): when NO visit stands on its map — the door's ZONE_CHANGE logged difficulty 0, which the game did for Voidscar Arena on a real +14, so no visit opened and the run, its END and its Σ all went missing — the START opens the keyed visit itself, named from its own dungeon field (else the last zone) at `KEYSTONE_DIFFICULTY` (8, the difficulty every keyed ENCOUNTER_START carries), closing whatever visit was current. Scanner and meter agree by construction: both read the START's name. Such a door logs 0 on every entry, so a ZONE_CHANGE at difficulty 0 whose map_id is the CURRENT unended keyed visit's RESUMES it (leaving a key mid-run is legal and costs nothing — the shop, a talent swap — and must never be read as a fail or a new visit); any other difficulty-0 change suspends as before. • A PULL ZONES IN the door that led to it did not (amendment, 2026-10-04, [the decision](../decisions/a-pull-zones-in.md)). On a real raid night the raid's difficulty was switched from Heroic to Mythic outside The Venomous Abyss and every door back in logged difficulty 0 (delves, Timewalking and Mythic dungeons log 0 too), so the Mythic pulls landed outside any visit and the Heroic visit stayed current, and live, to the end of the log. An ENCOUNTER_START while ZONED OUT, at an instanced difficulty (`meter::instanced_difficulty`: any nonzero id but Difficulty.db2's three of InstanceType 0 — 172 World Boss, 192, 230), on the map the last ZONE_CHANGE named (`last_zone_map`, the START's instance id being that map id), RESUMES the current unended visit when it stands on that map at that difficulty (a keyed one on the map alone; a keystone-difficulty pull on an unkeyed one is a key the log joined mid-run), and otherwise closes it and opens a NEW visit under the last zone's name at the pull's difficulty. Zoned in, the door stands. The pull settles the visit before its segment opens; the trash between such a door and its first pull stays outside. Every START that zoned in is a seed line, replayed through `Meter::seed`, which applies this rule alone and opens no segment. • A key JOINED MID-RUN (amendment, 2026-09-28) never sees its START — a pug member who joins after activation, or a disconnect that restarts the log — so the door's ZONE_CHANGE opens a plain visit and, before this amendment, the whole run closed as an unkeyed zone Overall: no level, no verdict, no timers, never a key card (coach retest 38: a Ruby Life Pools +12). A FINISHED CHALLENGE_MODE_END (a totalMs and a level) on the unended, unkeyed visit standing on its map therefore KEYS that visit from its own fields: `key_level` from the END's level, and the dungeon's timers from the one MapChallengeMode row on that map (`keystone_timers::pars_for_map`; a map holding two challenge modes stays unknown and the verdict falls back to the END flag). The visit is marked `joined`: its Overall clock is the span the log SAW, door to END — the damage before the join was never logged, so dividing by the key timer would understate every rate — while `official_ms` still carries the game's run time and the timed verdict reads it. The zeroed reset END on entry carries no totalMs, so it keys nothing. • CHALLENGE_MODE_END otherwise counts only for a keyed visit (the zeroed reset fired on entry, before any START, is ignored); it sets `completed` from its success flag and `official_ms` from its totalMs — the game's own run time, death penalties included — and it is TERMINAL: the keyed visit (and any open trash) closes right there. A finished key's clock has stopped and nothing resumes it, so it must not wait for the next instance to close: zoning out only suspends, so the night's LAST key would otherwise stay open to EOF, and a visit that never closes never becomes a history card. The rule keys on the END line alone — a key ABANDONED before its END is still merely suspended by zoning out and resumes on re-entry — and re-entering a finished key's map opens a NEW (unkeyed) visit rather than resuming it. The success flag only means "completed" (1 even in overtime), so a keyed visit's REPORTED outcome (`Visit::verdict`, shown as segment `success`) is the TIMED verdict against the dungeon's par (generated `keystone_timers.rs`, MapChallengeMode keyed by START's challengeID, with each dungeon's MapID beside it for a joined key): `official_ms &le; par` once the END fired; before it, a run already past par reports failed — OVER shows the moment the timer elapses (up to 15s per death late — live clocks carry no death penalties); an abandoned keyed run (END success 0) is failed; unknown challengeID falls back to the END flag. • Segments opened while zoned in carry the visit's ordinal. The visit's OVERALL (`Meter::overall`) is a synthetic `SegmentKind::Overall` segment: members' counters merged (tallies sum; identity maps union, later member wins; death order first-occurrence across members; each player's latest recap wins), duration = SUM of member durations (R7 per member, an open member cut at its last combat event), success = `completed`, name = `Visit::display_name()`. • EXCEPT: a KEYED visit's Overall clock is the key timer, not combat time — `official_ms` once the END fired (exact, frozen), else wall clock from `start_ms + KEY_COUNTDOWN_MS` (10s — the in-game timer starts when the activation countdown ends) to `end_ms`/now, clamped ≥ 0. Live estimates lag the in-game timer by 15s per death until the END corrects them. A keyed Σ row's per_sec is over this key clock — run DPS, not combat DPS. • Live and lazy paths both build the Overall by merging members, so index-then-lazy equals full replay by construction. A scan cut mid-visit splits the visit at `live_offset`: the `open_visit` prefix carries only members closed before it — bytes and clock — and the open member belongs exclusively to the live tail (which replays it from its first line), so merging prefix + live counts every member exactly once. • ZONE_CHANGE / CHALLENGE_MODE_* lines, and every ENCOUNTER_START that zoned in, are SEED lines: replaying them ahead of any slice (or the live tail, as `TailEvent::Seeds`) through `Meter::seed` reconstructs the visit table with file-consistent ordinals everywhere. A seed is never fed: a seeded START would open a segment ahead of the slice. In the combined segment list the Overall row precedes its visit's first member, and exists only once the visit has a member.
